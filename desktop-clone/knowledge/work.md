# Work tasks and verification

Choose Work in the new-conversation composer for tasks that require concrete actions, files, commands and checking results. Select a Project folder when working on existing files; otherwise supported file actions use the conversation's managed output folder. Keep compatible tool support enabled in the selected connection.

## Complete a task

Describe the desired outcome, constraints and relevant files. Work can plan a substantial task, use available tools, request missing information, and report results. Approvals are handled by TinyGPT's permission controls. Review the actual approval card before allowing a change. Existing authorizations can apply to subsequent actions, but denied actions must not be bypassed through another interface.

Questions use compact option rows and a single-line custom answer field. Longer answers scroll within that field. Choose an option or type your own answer, then submit; Work continues the same task after the answer is saved. The question-circle icon identifies the question tool in the working history. Inline questions, permission requests and browser sign-in handoffs leave the workspace browser usable while the task waits. Stop task cancels the pending task instead of submitting an answer.

Commands take a program and separate arguments. Long-running jobs have status and stop controls; a started job is not a finished job. Commands run with operating-system permissions and are not a general OS filesystem sandbox. Do not assume selecting a Project prevents every effect of an approved program.

## Bundled Python, Node, npm and npx

Work commands, the Coding agent and workspace terminals use the same bundled Python 3.13.18, Node.js 24.22.2, and npm/npx 11.19.1. No separate system installation or first-run runtime download is needed. Python is available as both python and python3, with its standard library, SSL, SQLite, venv and python -m pip. Node runs as a standalone executable. TinyGPT places these tools before system installations on the command path and keeps package-manager configuration and caches separate from your usual user configuration. If bundled files are missing or invalid, TinyGPT reports an unavailable-tools error instead of silently selecting a system runtime. The desktop packages target Windows x64 and Apple Silicon macOS.

Install additional Python packages in a Project virtual environment: run python -m venv .venv, then use .venv/Scripts/python.exe on Windows or .venv/bin/python on macOS with -m pip. Package installation into the shared bundled Python is disabled by default. Each Project can keep its own packages without changing the Python used by other chats. npm and npx use the bundled Node; npm install and npm run work in the selected project. npx can run project-installed commands. Installing or downloading additional dependencies still uses the normal command permission controls and may require internet access. Offline use works for built-in libraries and dependencies already available locally; the bundle does not include every Python/JavaScript library, native compiler, Git, or other external program. Terminals can still run other installed system tools. These runtime choices do not restrict commands to an OS sandbox.

## Inspect results

Work’s working history shows prose, thinking and tools in their recorded order. Coding work appears inside an inline **Coding agent** section, containing its own updates and tools. It opens while active and collapses when that coding call ends; the assistant can continue reviewing afterward. The outer history collapses when the final answer is confirmed. This same presentation is used on the mobile companion with a bounded recent history that preserves the parent of retained coding tools. Mobile does not expose the full native session or raw tool results.

Review changed files, diffs, checks and command exit results. Work should verify outputs with tools and report material limitations. Guarded Undo checks whether reversal is safe; it cannot undo external messages, purchases or arbitrary command side effects. Stopping a task cancels ongoing work where supported but does not reverse completed actions.

Working-history icons distinguish file, browser, command, skill and planning actions. Individual action icons take precedence over a shared family icon. Plugin-provided skill actions can therefore use a different icon from TinyGPT's built-in skill tools. Icons describe activity; they do not establish account access or permission to execute a tool.

## Smaller changes and output limits

Work and the Coding agent save a small working result first, then improve it with focused edits. Each native write, edit or patch accepts at most 16 KiB of UTF-8 change text; finished files can be larger. Oversized changes are rejected before execution. Incomplete tool calls are never executed, and an interrupted response does not mean a file was saved. Commands still use OS permissions; this file-tool limit is not an OS sandbox.

When the Coding agent reaches its output limit, Work preserves its session ID and reports whether it ran out during thinking, tool preparation or an answer. A follow-up coding attempt automatically resumes that failed session when no other session is specified. Continue restores this recovery context from the selected conversation branch, keeping existing file changes and current permissions.

Two output-limit failures in the same runtime without a further recorded file change pause Work with an actionable message. Directory listings do not reset that safeguard. Review the saved changes, revise the instructions or select another effort/model, then Continue. This prevents repeated fresh attempts from consuming the model indefinitely; it does not guarantee that a local model can finish every task. The configured total output allowance is unchanged.

## Long tasks and local context processing

Each model request includes the active conversation context: instructions, tool definitions, user requests, earlier assistant reasoning/replies and tool outcomes. Input-token totals can therefore include substantial existing history. A local prompt cache holds temporary computed state for a matching token prefix; saved conversation history is separate. Changes to an earlier prefix, cache eviction or unavailable model state can require processing old input again. An input-token total alone does not tell you how many tokens were reused.

For declared local llama.cpp connections, Work explicitly requests prompt caching and native progress counters. Diagnostics distinguish cached tokens from newly processed tokens and record character counts by payload category and how many complete messages remain unchanged at the front. Character counts are not exact tokenizer counts or proof of a cache hit. These records contain counts, not prompts, reasoning text, URLs or credentials.

The shared date/time note is a reply-start snapshot. It stays unchanged throughout a tool loop and retries, rather than rewriting a clock in the leading system instructions for each call. A new reply or resumed run gets a fresh snapshot. Work's request-shape measurements run after this shared note is applied, so they describe the body actually sent to the provider. A stable prefix enables cache reuse; deliberate history edits, changed tool definitions or missing model state can still cause a cache miss.

For local OpenAI-compatible Work runs, callable tool definitions stay fixed throughout a run. A bounded set of common browser tools is selected at startup. Additional tools and connected-plugin actions are discovered through load_tools; their parameters arrive as conversation data and invoke_tool calls the selected action through the normal host validation and approval flow. Discovery does not replace earlier tools or grant permissions. Smaller context windows may discover some browser actions through this same interface. This policy applies to Work; Chat, Bot and other provider protocols retain their existing tool-loading behavior.

Large native file/command results and browser observations are bounded when first returned. Work's native text reader returns a contiguous page of up to 2,000 lines or 50 KiB, including its continuation instructions, without a second head/tail excerpt that could hide the middle of that page. Its offset is a 1-based line number and limit is a line count. Continue with the returned offset to read more, or use a narrower line range. Saved-observation offsets are character offsets in an earlier captured result, not line numbers or a fresh file read. Large command/browser results can still use bounded excerpts with exact saved observations available for retrieval.

Existing history stays unchanged while context capacity is healthy. Local Work cleanup starts when measured context pressure reaches about 85% of the input budget and targets about 60%, leaving space for further tools and replies. Older long completed reasoning and large observations are retired only if the batch can reach that lower target. Otherwise Pi's normal compaction creates a checkpoint before the next model request; small edits do not repeatedly rebuild the same large prefix. For older successful large write/edit actions, cleanup retires the call and its matching result together into an explicit historical execution note. Exact arguments and results remain in a scoped saved observation; archive notices are never inserted into the content or edit arguments of a historical tool call. Failed, pending and recent call/result pairs remain intact. Current instructions, user messages, successful outcomes and recent reasoning remain available. Signed reasoning and other providers do not use this local reasoning-retirement policy. Archiving can invalidate a cached prefix; it reduces context growth but does not guarantee cache reuse or a particular speedup.

When continuing an existing local Work chat, TinyGPT repairs older host-generated write/edit argument placeholders from the original native call on the selected session fork. It preserves the original session and other branches. This repairs model context; it does not rewrite already-created project files or erase earlier mistakes. Use current file reads before making further changes. Exact native history and scoped observation retrieval remain available, including after Continue.

With Diagnostics enabled, active local runs record supported NVIDIA GPU activity, memory, clocks, power, temperature and limiting states about every ten seconds. Device-wide readings are correlated with request IDs and timing; they do not establish that one request caused all GPU activity. Counts of other compute processes may omit graphics workloads or unavailable driver data. Other devices report unavailable counters. Sampling stops when local runs finish, Diagnostics is disabled, or records are cleared. App-managed model timing, generation rates, acceleration acceptance and skipped prompt snapshots are saved as numeric events, so they remain inspectable after the native log rotates. Records use existing local retention and are not automatically uploaded.

Settings → Work settings controls Work effort, shared file/read/write/command approval policies, diff markers and code font size. Effort availability depends on the selected model. Presentation or document creation also depends on available tools and formats; a task description alone does not install missing software or establish a successful export.
